# 为什么研究Agent推理需要通过架构视角入手？
我们假设现在需要去订一张去上海最便宜的机票：
    Agent首先会调用搜索网站或调用购买机票的API，解析并返回的几十条结果，调用MCP去比较价格/时间，调用支付API并完成任务，最后会告诉你结果。

如果这个任务失败了：
    不从架构视角入手，可能会想：
        1.是不是模型不够强？ ---> 调用上下文更大更强的模型 ---> 成本明显上涨
        2.Prompt没写好?  --->通过学习prompt engineering写更好的prompt --->可以解决问题，但也可能会消耗更多的token
    
    从架构视角入手会多思考一层:
        1.搜索 API 返回了几十条航班，全部塞进上下文 ---> 内存怎么管理？
        2.模型要做几十次比较才能找到最便宜的 —— 这些步骤串行还是并行？谁来调度？
        3.支付这一步如果失败了，前面的搜索结果还在不在？状态怎么保持？
        4.整个流程跑了 30 秒，瓶颈在哪？延迟从哪来？

不从架构视角入手，也可以解决问题，但是容易使推理成本明显上涨，问题本质没有解决，只是推迟了。

如果我要买1000张去不同地区的最便宜的机票呢？
    从系统架构视角入手：
        1.并行化：1000个目的地拆成 1000个独立子任务，并发执行，每个只处理自己的结果
        2.外部筛选：在进入 LLM 之前，用传统代码先按价格排序、只保留 top 3，模型只看几百条而不是几万条
        3.分层Agent：一个总Agent负责拆任务，多个工作Agent各自处理一个目的地，结果汇总后再做最终决策

训练出再聪明的模型，如果推理时的任务分解和资源调度设计得很差，在真实规模下一样会崩。

常见的几类Agent推理失败原因:
    step_budget_exceeded_before_finish
    missing_required_actions：模型提前结束，没有按要求调用必要工具。
    incorrect_final_answer：工具调用流程看起来对了，但最终答案仍然算错或抽取错。
    tool_execution_error：动作格式不合法，或者工具输入表达式错误，导致执行失败。
    JSON 解析失败或输出格式漂移：模型没有按约定返回结构化字段，loop 会被中断。
    检索噪声与歧义：如果 notes 更长、更乱或有冲突信息，search 工具可能把模型带偏。
